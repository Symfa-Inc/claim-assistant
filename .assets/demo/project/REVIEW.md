# REVIEW: Claim Assistant demo (v1)

Delivered: `../demo-claim-assistant.mp4` (66.5 s, 1920x1080, 30 fps, H.264 High yuv420p, AAC LC 48 kHz stereo,
19.7 MB, CRF 20), `../poster.png` (t = 3.5 s, lossless from the composition).

## Creative calls
- Storyline A, "One claim, start to export" (see `../STORYLINES.md`); B ("the misread") and C ("three questions")
  not built. One continuous take inside the real app; the only transition between chapters is a full-frame #f8fafb
  sheet led by a 16 px teal bar (the app header's accent bar), 4 uses + the end card. Inside chapters the camera does
  the work (1.333x to 3.0x, power2.inOut, one move at a time, never while a callout is up).
- No caption strip. On-screen words: 3 centred headline sheets (<= 6 words, 104 px Plus Jakarta Sans 700) and
  7 callouts (30 px) anchored to the element they describe, each up 1.55-2.55 s.
- UI = DOM rebuild of the captured page, not screenshots: the app's own compiled Tailwind CSS (captured from the
  running dev server), the app's class strings and icon paths, the real `/process` response, and the PDF pages
  rendered at 216 dpi (crisp up to ~4x). The native `<select>` popup cannot be captured headless, so it is drawn
  in the app's popover style.
- Data: backend on :8010 (`CORS_ORIGINS` env), frontend on :3010 (`next dev --port 3010`); the frontend's API base
  is hard-coded to `localhost:8000`, so the capture browser routed those requests to the recorded response instead
  of editing code. Both servers were stopped; the files the dev run created (`frontend/AGENTS.md`, written by
  `next dev`, and `backend/data/runs/20261026_230514/`) were removed. No app code was touched.
- AI output: OpenAI and Azure keys were present (`backend/src/claim_assistant/.env`, not printed), so all four
  sample forms were processed for real (87-139 s each). The Florida handwritten form was chosen: its real output
  carries a real misread (COMPANY NAME "Pac Ecom Logistics" 36%, read from the D.B.A. line). Checked against the
  form: the summary's facts (Portland OR loading dock, carton, right knee + left wrist, wet spot, supervisor + first
  aid, within 2023-01-12..2025-01-12) all match; "Low overall OCR match confidence (0.98)" matches the computed
  0.976 (policy number read as "POL 987654321" with a space). The film shows the verdict honestly as "uncertain".
- Copy checked against the data: "54 fields read, 31 flagged" (31 = the app's low-confidence count, which includes
  6 fields with no score); the sheet was changed from "Every value, traced to the page" to "Values, traced back to
  the page" because one non-empty value (RETURNED TO WORK checkbox) has no evidence box.
- Font: Plus Jakarta Sans (the app's `next/font`), the captured latin woff2; it renders correctly in the live app.

## Fixed during review
- The render page does not apply the captured `html { line-height: 1.5 }` preflight to the scene (HyperFrames mounts
  the template's styles under its own root), so table rows were shorter in the render than in the measuring page
  and every scrolled cursor target landed ~118 app px off. Fix: restate the preflight on `#ca-app`; verified the
  render against a plain-Chrome seek of the same composition (difference image black apart from PDF resampling).
- Tailwind preflight font stacks (emoji, SFMono, "Plus Jakarta Sans Fallback") failed lint; rewritten to the one
  family at build. Hover/focus rules and CSS transitions/animations stripped (they run on the browser clock).
- Confidence bar overlay escaped its 3 px track (missing `relative`) and drew a large emerald disc; fixed.
- Processing/empty right-panel states had forced 730 px heights; now natural height as in the app.
- PDF push showed a strip of the results panel; now framed at 3.0x with the right edge in the gutter.
- Callouts re-placed so they cover whole cells, never half a number; holds lengthened to >= 1.5 s on screen.
- Approve label swap is now out-then-in (the old crossfade showed "✓ 179%" for two frames).

## Weakest shot / known limitations
- 45.3-50.6 s: the queue is cleared in fast-forward (27 approvals, one per 0.1 s). It is time-compressed and the
  rows it approves include real extraction errors left unedited (e.g. DATE OF DEATH 2024-09-23 at 20%, which is
  the return-to-work date). A careful viewer could read that as the reviewer rubber-stamping. With more time:
  edit that row too, or frame the fast-forward tighter on the approve column.
- 12-14 s: the real "Analyzing document..." card is short, so the whole-app frame is mostly empty for ~2 s.
- The real processing takes ~110 s; the film shows 2.4 s of spinner.
- Fonts in the hook's Key Fields header (16 px) sit under the 28 px floor; decorative product styling.

## v2 (owner: "blurry/soft overall") -> `../demo-claim-assistant.mp4` (replaced v1)

**Root causes.**
1. Capture at device scale 1: HyperFrames rendered the 1920x1080 page at DPR 1, so every glyph, rule and the PDF
   raster was sampled once at output size, with no supersampling. The handwritten PDF page was a 216 dpi PNG
   (1836 px wide); at the 3.0x push it is shown 1341 px wide, only 1.37x its on-screen size (target >= 2-3x).
2. Encoder: v1 was HyperFrames' x264 at CRF 20, bframes 0, 2.17 Mbit/s video. Static holds were close to the
   lossless frame, but camera moves (a large part of the film) lost detail: snapshot vs video PSNR 37-38 dB and
   about 6 % lower Laplacian sharpness on moving frames.

**Checked and clean (no change needed):** no `will-change` anywhere; GSAP `force3D: false` and no 3D transforms
or `translate3d` in the app CSS; every blur-in ends on `filter: none`; no `image-rendering`; Plus Jakarta Sans
loads (not a fallback). A CSS `zoom` rendering of the same frame was identical to the transform-scaled one, so the
camera's 2D scale is not a source of softness.

**Changes.**
- PDF pages re-rendered at 432 dpi (3672 x 4752 px, 2.7x the 3.0x-push size at 1080p), hook crop from the same
  page (3412 px for an 868 px slot).
- Backdrop filters removed where they did nothing (sticky header) and switched on only while the Export dialog is
  open (a full-app backdrop-filter layer was present, at opacity 0, for the whole film).
- Render at DPR 2: `npx hyperframes render --quality delivery --resolution landscape-4k --crf 8` (the CLI scales a
  1920x1080 composition with deviceScaleFactor 2 -> 3840x2160), then a Lanczos downscale and a fresh encode:
  `ffmpeg -vf "scale=1920:1080:flags=lanczos+accurate_rnd+full_chroma_int,format=yuv420p" -c:v libx264 -preset
  slow -crf 16 -tune animation -profile:v high -movflags +faststart -c:a copy`. On a 12 s busy segment
  `-tune animation` scored highest of default/film/animation at equal CRF (42.5 / 47.9 dB on moving / static
  frames vs 41.4 / 46.8 default).

**Result:** 66.5 s, 1920x1080, 30 fps, H.264 High yuv420p, video 3.14 Mbit/s (was 2.17), file 27.8 MB (was
19.7 MB), audio unchanged (-16.9 LUFS, true peak -1.6 dBTP). Laplacian sharpness v1 -> v2: 13.2 s (1.33x)
1955 -> 2004, 15.4 s (camera move) 3066 -> 3501, 26.0 s (3.0x PDF) 5963 -> 6486; 100 % crops show finer
handwriting strokes and cleaner glyph edges in motion. Re-checked on v2: callouts a-g still fade in with 0 dips,
static holds 0 changed pixels, layout and timing unchanged.

**Rebuild (v2):** as above, then
`npx hyperframes render --quality delivery --resolution landscape-4k --crf 8 --output <4k.mp4>` and the ffmpeg
line above to `../demo-claim-assistant.mp4`.
